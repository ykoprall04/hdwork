# Writer FIFO + fence: review before a separate deployment approval

Implementation is prepared and tested in development. No production database operation, task change, deploy, restart or Telegram call was performed for this change. Public web and other bots must remain available. This is not an executable cutover plan or an activation approval.

## Code and protocol

Set only `HDWORK2_COURIER_WRITER_V2_BOTS_JSON=["hdworkopsbot-testing"]` in a reviewed candidate web environment. Do not turn on global FIFO/send/poll flags for this writer rollout. Absent/empty scope preserves legacy behavior. Invalid scope or missing live-chat prerequisites fails startup. Startup validates the existing FIFO columns, minimum FIFO grants and the control row; it never creates schema, grants or the row. A closed row allows web startup and reading; new target-bot outbox writes return a retryable 503 and their enclosing business transaction rolls back.

The shared `MysqlStore.enqueueOn` used by chat, operational replies and system alerts enforces the scoped profile. It obtains the fence shared row lock inside `MysqlStore.transaction`, then the existing FIFO allocator resolves the real order/route and allocates `conversation_key`, `conversation_seq`, `fifo_order_id`. The insert, allocation, chat/business writes and audit commit together. Scoped callers outside that transaction wrapper are rejected. Explicit legacy constructor flags cannot bypass the scoped profile. Unknown/missing order proof is rejected as `WRITER_FIFO_ORDER_REQUIRED`; it is not assigned a fabricated order or silently enqueued as deliverable. Before deployment verify that any enabled system-alert recipient for this bot has a genuine matching order anchor; an arbitrary alert anchor will now be rejected. Other bots retain their previous path.

The existing `hd2_courier_lanes` table holds one reserved control row per scoped bot. Its key is `43639aa660678fd848c38b72f1ee6bd12fcc9d7d5589444fb1712a5ff4e0d421` (SHA256 of the protocol name). It is not a delivery lane and must be excluded from conversation-count reporting. No DDL or new GRANT is needed: existing lanes SELECT/INSERT/UPDATE and audit INSERT suffice.

`next_seq` on this reserved row is a monotonic epoch: initialize at 2 (CLOSED), open increments to 3, close to 4, and so on. Even is CLOSED; odd is OPEN. Never delete/reset the control row or reuse an epoch. Missing/corrupt state fails closed. Ordinary conversation lanes keep their existing semantics. No outbox row points at the control key.

Writers hold `FOR SHARE` until the enclosing transaction commits or rolls back. Control uses `FOR UPDATE NOWAIT`. If a writer is in flight, close returns `WRITER_FENCE_BUSY` and no successful drain receipt; the operator can inspect and explicitly retry. Once close commits, writers that started earlier, including those with an earlier repeatable-read snapshot, observe CLOSED through a current locking read. Fence change and its audit are atomic. A persisted fence survives writer process/connection restarts without a lease timeout or an automatic reopen.

Every open/close requires the expected epoch; repeat close at the same epoch is idempotent, but an old epoch cannot reopen or attest a fence that was opened/closed again. Recheck `assertClosed(pool,{botId,expectedEpoch})` at each cutover boundary. This is a **cooperative** barrier covering patched, explicitly scoped writers. It cannot stop old code, arbitrary direct SQL, a DBA, or sender ACK updates. Do not claim quiescence until all target-bot writer instances use the reviewed code/config, old writer processes and requests have drained, and the sender is separately stopped. Do not report web PIDs as gone: the web stays alive while the bot's outbox is fenced.

## Operator control and real database binding

`scripts/control-courier-writer.js` defaults mutations to PLAN without loading the session or credentials. Inspect is read-only. Actual initialize/open/close additionally require `--execute` and a fresh operator approval bound to action, bot, epoch, account, reason, session SHA, runtime config path/SHA and expiry (at most one hour).

The supplied `scripts/lib/production-courier-writer-session.cjs` is a real binding, not a success stub. It verifies the original pinned Courier runtime configuration and source/service files, validates its pinned production plan and bot identity, decrypts only its existing DB-password DPAPI reference, and checks `hdwork_courier@localhost` on `127.0.0.1:3306/hdwork2` with `courierSendChatFifo` grants. It returns a session restricted to `hdworkopsbot-testing`. It does not read/decrypt Telegram token, identity key or service key, and starts no service. It has **not** been invoked against production in this development task.

After the approved release's complete source/dependency manifest is verified, a PLAN example in PowerShell is:

```powershell
node <REVIEWED_RELEASE>/scripts/control-courier-writer.js --action close --bot hdworkopsbot-testing --epoch <INSPECTED_EPOCH> --session <ABSOLUTE_SESSION_FILE> --session-sha256 <SESSION_SHA256> --runtime-config <ORIGINAL_PINNED_RUNTIME_CONFIG> --runtime-sha256 <RUNTIME_SHA256> --account hdwork_courier@localhost --operator <OPERATOR> --reason <REVIEWED_REASON>
```

For inspection, change action to `inspect`; omit epoch, operator and reason. It authenticates read-only using the pinned binding. Do not copy credentials to command lines or new plaintext files. For actual mutation, an owner separately completes and signs/reviews the approval template in `ops/examples/courier-writer-approval.PLAN_ONLY.json`, and supplies `--approval <ABSOLUTE_APPROVAL_FILE> --execute`. The checked-in template deliberately has approved=false, null pins/expiry and cannot authorize anything. Do not run these commands during preparation.

## Separate deployment proposal

1. Regenerate an immutable release from the reviewed commit, including the web dependency graph and the operator CLI/session dependency graph. Verify hashes and package-lock against the installed runtime. Stage into a new private snapshot. Keep the existing frontend, secret bundle, Telegram settings, bot routes, session/signing keys and live web files unchanged. Do not use stale candidate pins from the earlier preparation.
2. In a fresh read-only preflight, verify current schema/grants, bot scope, current DEAD metadata and pending queues; do not assume the historical 109 SENT / 18 DEAD snapshot is still current. Verify the reserved key is absent or matches a previously reviewed fence; unexpected existing state is STOP, never reset. Check all producers of target-bot outbox and genuine alert/order anchors. Do not rerun 015–017, GRANT, administrative18 or historical retry/reset tools.
3. Obtain separate approval for initializing the reserved control row CLOSED and the deployment/handoff of the compatible web writer. Initializing the row while old code is live is **not** quiescence evidence. It affects no other bot's row and changes no message state. Do not initialize an existing row again.
4. Use a separately reviewed web handoff procedure that preserves public availability and drains the old target writer completely. No deployment/restart command is authorized here. If the current host cannot provide the required handoff, stop for an explicit operational decision; do not fall back to killing the web or stopping other bots. Boot the candidate with the exact one-bot scope and existing secrets. Verify installed hashes, scope, real startup probes, web health and unaffected other-bot routing. A rejected target outbox write must roll back its chat/business writes. No Telegram test send is permitted.
5. Only after all target writer instances are proven compatible, inspect/close the exact fence using the current epoch and scoped approval. BUSY, partial rollout, changed pins, queue activity or unknown provenance is STOP. A closed barrier covers outbox writers, not all shared database tables. Do not label a full shared-database snapshot globally quiescent while other bots continue to write; the paired-backup binding must define and verify its bot-specific recovery scope without disturbing them.
6. Keep the sender disabled. Refresh bot-specific queue, legacy DEAD, worker lease, SQLite ACK and fence-epoch evidence. Capture and restore-rehearse a coherent recovery point with the reviewed backup binding. Only then perform separately approved marker-only administrative recording and the flags-off Courier installation/health phase. Administrative metadata never releases FIFO or makes old messages deliverable. Opening the writer fence and enabling Telegram are separate actions with separate approvals; neither happens automatically after startup, health or a timeout.

## Rollback contract

First close/assert the bot fence with a current epoch and verify the sender remains disabled. Retain the scoped configuration, control row/epoch, FIFO-capable/fence-aware MysqlStore and its dependencies in any compatible web rollback. Preserve online reads and other bots. The integration test exercises rollback with those invariants, not a claim that arbitrary historical binaries honor the barrier. A full rollback to an unfenced legacy writer, or removal of the scope flag while outbox writes remain possible, is unsafe and requires a separately reviewed way to block only this bot before that code can serve requests. Do not run that rollback automatically.

`scripts/lib/courier-writer-rollback.cjs` supplies the read-only rollback guard: compare the actual source bytes of the retained writer/fence/FIFO modules between the verified current release and candidate, require unchanged bot scope/global routing flags, and check the live CLOSED epoch through an authenticated pool. It rejects a legacy writer or removed scope before any installation. It does not install files, control tasks, restore data or replace verification of the full release manifest. The isolated test invokes it against real candidate files and the real fixture database.

Never restore the old MySQL backup automatically: it contains ten QUEUED rows that are now DEAD. Never rewind the journal, reset lanes, erase epochs, backfill/sequence or resend old rows. Preserve all eighteen DEAD rows and their administrative history. Runtime rollback is not database restore. Reopening the fence must use a separately approved current epoch after the compatible writer is verified.

## Automated evidence

`npm run test:courier-writer` runs offline scope/approval checks. `npm run test:courier-writer:mysql-isolated` additionally starts an owned MySQL 8.4 Windows instance with a unique named pipe and TCP disabled; only synthetic data is used. It tests actual chat sends, same-request concurrency, lane allocation/order, real claim/ACK ordering with synthetic receipts, transaction rollback, busy/closed/stale fences, Node process restart, repeatable-read races, compatible rollback, another bot and full preservation of 18 synthetic DEAD rows. A fixture account receives the exact existing chatWriteFifo policy to test real least-privilege SQL. Fixture-only grants are not production GRANTs. A PASS receipt is written only after every integration scenario passes. No production credentials or Telegram are used.

The remaining production gates are approval and actual rollout/version coverage, fresh scoped recovery/audit evidence, and a reviewed immutable delivery runtime with real no-send health checks. Isolated tests establish implementation behavior; they do not assert that production has been changed or activated.
