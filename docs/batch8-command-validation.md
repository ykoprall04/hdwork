# Batch 8 — validation commands and historical TIAL duplicates

Preparation only, no service/worker/migration/Telegram activation. SQL 004/005 (MySQL 8.0.13+, per-statement DDL commits) and Batch 7 isolation guards were reviewed; additive **006** is manual only. Old rows are never deleted or overwritten. No legacy hd_b2c, Preview or original bot changes.

## Architecture and compatibility

`contracts/b2c-commands.json` is the shared lightweight field specification. Node and Python independently extract/validate. Package the whole repository (including contracts/) when deploying the new courier later; no external package required. Normalized command types: order, config_psb, mo, req. A prefix before AO/PDA/MO/DO is not fixed; matching is case-insensitive, output preserves identifier case, business duplicate matching uses uppercase. Fields accept colon with/without spaces. Missing/blank/dash mandatory fields and ambiguous repeated labels are rejected. Optional missing/dash values become null. Identity extraction ends at underscore; optional Service is validated if supplied. /req original text remains unchanged in restricted storage.

Python command gate takes explicit groups with `chatId`, `threadId`, `threadMode`, `profile` (TIAL1, TIAL2, SOLVER1). Configure `COURIER_COMMAND_GROUPS_JSON` privately; IDs are not hardcoded. No topic is inferred to be General. Unknown groups/topics and edits are not forwarded/replied. Non-command status replies pass to Node for workflow/actor authorization. Invalid submissions receive a direct reply with fixed reasons/field names, never an echo of customer data, and do not reach Node/MySQL. Valid submissions use existing HMAC/loopback/event retry. The CLI requires reviewed groups and an absolute private `COURIER_REJECTION_DB` journal path before any network cycle; all existing disabled/default flags remain.

The rejection journal is local stdlib SQLite, storing only bot/update hashes. It reserves before send to prevent repeated rejection on replay/restart. **At-most-one attempt**, not guaranteed delivery: crash/timeout after reservation can lose a rejection. Repeated retries never intentionally send again. Journal ACL, backup/retention and a single courier owner are prerequisites; no purge or second polling instance is activated. Valid event ACK loss is still safely retried by Node idempotency. The existing Node outbox retains its at-least-once delivery limitation, distinct from rejection replies.

Node groups opt in with `commandProfile` using the same profile names. TIAL1/TIAL2 require module TIAL. All command types submitted there remain in that workspace, separated by `command` in the model/web. Solver groups use the configured existing module. The old labelled-line grammar remains for old **non-command** events/tests; slash commands without a command profile fail closed. New commands revalidate in Node before any order row creation (invalid events from an internal sender may remain in the restricted inbox/audit). This is a data validation gate, not a transfer of workflow decisions to Python.

## Schema / full-history duplicate handling

006 adds nullable command, raw text, JSON fields, sender ID, Telegram timestamp and reserved duplicate_decision columns to orders, plus a global HMAC reservation table hd2_tial_keys. Existing rows stay nullable. Full original messages/fields (including NIK) are restricted database data and never included in the web DTO. Inbox also retains the original envelope. No UNIQUE on SC/IN in the orders table.

Only /order uses a global reservation keyed by extracted full SC/IN, independent of bot/chat/date, in the same transaction as order/audit/inbox. A reservation winner becomes canonical; every subsequent original message gets its own DUPLICATE row linked to canonical even if DONE. config_psb/mo/req never use the business reservation. Same Telegram update/anchor remains idempotent. Lock contention/deadlocks use existing rollback/retry policy, never partial commit. Concurrent arrival means first committed canonical, not a claimed chronological Telegram global ordering.

When a key has not been reserved, Node also searches existing canonical TIAL rows with matching full SC/IN, including command=NULL historical rows. This is not an automatic historical migration: **before activation**, review/backfill canonical references and command classification in a separate approved plan, covering data outside hdwork2 too if applicable. No code can guarantee all-history duplicates for history that was never imported or normalized. Do not enable the new workflow until that coverage is approved. Do not change identity HMAC key across instances without a reviewed rekey; all instances must share the same approved key. Lookup without an expression index may scan historical orders; measure EXPLAIN and capacity in disposable before use.

Lanjut Cek / Tolak Duplikat are inactive planned decisions (CONTINUE_CHECK / REJECT_DUPLICATE). Future authorized transaction must record decision, actor, timestamp and an append-only hd2_audit action (DUPLICATE_CONTINUE_CHECK / DUPLICATE_REJECTED); duplicate_of and conversation history must survive. No endpoint/function mutating these decisions is exposed now.
